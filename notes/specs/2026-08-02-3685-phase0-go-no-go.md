# carina#3685 Phase 0 go/no-go: WASI 0.3 (wasip3) provider boundary

Status: decision note (2026-08-02)
Parent: carina-rs/carina#3685
Evidence: `../spike-3685-phase0-findings.md` (spike branch `issue-3685-wasip3-spike`, not merged)

## Verdict

**GO for Phase 1.** Both technical exit criteria from the issue pass, with
the evidence quality Stage A lacked. The one caveat that must travel with
this verdict: all evidence is mock-provider evidence. The real-infra gate
(the #3400 registry-dev plan and the #3254/#3318/#3320 apply shapes) stays
in Phase 2 and is a strictly stronger test than anything run here.

## Exit criteria assessment

1. **Async export shape confirmed in the artifact — pass.** The built mock
   component (`sha256 efb145d4a3350ac43dd3cb605586dd2890b68f42370189e71168ba46c3af6ab8`)
   was dumped with `wasm-tools component wit` and shows exactly the six I/O
   exports (`initialize`, `read`, `read-data-source`, `create`, `update`,
   `delete`) as `async func` and every metadata/validation/normalizer export
   as sync — the Option C split held; whole-interface async escalation was
   not needed. Verified independently by the reviewer against the artifact,
   not taken from the implementation report. This closes the exact
   verification gap that sank Stage A.
2. **No livelock in the stress suite — pass, mock-scoped.** The five
   `multi_instance_wasi_http_initialize_*` shapes from the reverted Stage C
   suite (443e5260) were resurrected and run for 20 full-suite iterations
   (100 stress executions) on exact wasmtime 47.0.3, each suite completing
   in 12.425–12.555 s (spread 0.130 s), zero timeouts, zero
   `NeedWork`/`StartImplicit` markers. The guest path is genuinely async —
   the p3 transport has no `pollable.block()` to hide behind. Per the 3400
   handoff, green mock stress is necessary but not sufficient evidence for
   the real-AWS workload; this note does not claim the historical livelock
   is fixed.

Additionally, exact-47 end-to-end works: 9/9 integration tests
(initialize + CRUD) and 169/169 nextest across host/SDK/mock, reproduced
by the reviewer.

## Working toolchain (record)

- **Guest**: stable Rust 1.95.0, target `wasm32-wasip2` — a *hybrid*
  component: std contributes wasi 0.2.9 cli/io/random imports while
  provider HTTP/clocks and the canonical async exports are p3. Built with
  wit-bindgen 0.54 (`macros,async`) as the direct generator plus the
  `wasip3` crate 0.7.0+wasi-0.3.0 (its wit-bindgen 0.57.1 runtime) and the
  final `wasi:http@0.3.0` / `wasi:clocks@0.3.0` WIT. The 0.54/0.57.1 split
  was an offline-cache artifact of the spike environment; Phase 1 should
  unify on one wit-bindgen (0.60 is current).
- **Native `wasm32-wasip3` is blocked** on this machine: the nightly
  (1.99.0) target spec emits `--cooperative-threading`, which rust-lld
  rejects, and no libc/sysroot exists for the Tier 3 target. Not a Phase 1
  blocker — the hybrid route needs only stable Rust — but the hybrid is not
  the clean final toolchain; revisit native wasip3 when the Tier 2
  promotion (rust-lang/compiler-team#1001) lands.
- **Host**: wasmtime / wasmtime-wasi / wasmtime-wasi-http pinned `=47.0.3`
  with the `p3` features, component-model-async on, six async exports
  driven through `Store::run_concurrent` + `Accessor`. Hybrid linker set:
  p2 CLI/io/random for std, p3 clocks/http for the provider path. rustls
  0.23 (aws-lc) for the default p3 transport. One 45→47 API delta was hit
  (`cli::exit::add_to_linker` lost its `LinkOptions` argument).

## Compatibility posture decision

Issue step 5 sets the default: **(a) hard break, p3-only**, unless the
spike shows provider repos cannot ship p3 promptly. The spike shows the
opposite — the p3 guest builds on stable Rust in seconds, so aws/awscc can
ship p3 artifacts as soon as their SDK/trait migration lands (the Stage A
provider PRs remain the template). Decision: **(a) hard break**.

The spike report recommended a transitional dual-world host instead. That
recommendation is declined: the project's standing policy is no backward
compatibility, and the 3400 design note already rejected a parallel legacy
interface (its Option B) because it keeps the broken sync-export state
representable and doubles the protocol surface. The transition mechanism is
the fail-fast instantiation error — an old p2 component fails to
instantiate with a clear "rebuild your provider" message — exactly the
Stage A breaking-change posture. The legitimate concern behind the
dual-world suggestion (wasmtime's p3 module is documented experimental and
outside semver) is addressed by sequencing and pinning, not by maintaining
two hosts.

## Conditions attached to the GO

1. **Pin exact wasmtime versions and re-verify per bump.** The p3 module is
   experimental/outside normal semver; every wasmtime bump in Phase 1+
   re-runs the stress loop.
2. **Port the HTTP policy hooks in Phase 1, not later.** The p3
   `WasiHttpHooks` seam is confirmed viable (request + `RequestOptions` +
   response-future control ⇒ allow-list, tracing, per-request timeout), but
   the spike ran default hooks. Phase 1 ships `AllowListHttpHooks` on p3
   with the allow-list/IMDS/timeout semantics preserved, and repeats the
   stress loop through those hooks.
3. **Keep the 20-minute hard timeout and instance poisoning.** The HTTP
   hook only governs HTTP; a guest can still wait elsewhere and cancellation
   semantics on p3 are unverified. Re-evaluating poison/timeout is Phase 3,
   after soak, as the issue already stages it.
4. **The real-infra gate is Phase 2 and is non-negotiable.** Only a p3
   aws/awscc artifact planning the #3400 registry-dev stack and applying
   the #3254/#3318/#3320 shapes can retire the livelock history. Any
   real-provider stall gets the
   `RUST_LOG=wasmtime::runtime::component::concurrent=trace` procedure and
   a check for `NeedWork`/`StartImplicit` cycling before any other
   diagnosis.
5. **Phase 1 normalizes the spike's shortcuts**: one wit-bindgen version,
   no path patches, mock CI target updated, PROTOCOL_VERSION posture
   re-checked against the final WIT type shapes.
